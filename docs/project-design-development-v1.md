## 1. 项目定义

### 1.1 当前产品目标

当前要交付的是一款：

> **PC 优先、单人本地游玩、以视觉小说阅读和自由文本输入为核心的 Fate 风格 Agent Game。**

玩家应能在持续存在的世界中：

- 阅读场景、对白和角色表演；
- 用自然语言说话、观察、移动、互动和参与战斗；
- 与拥有长期身份、主观认知和记忆的角色持续相处；
- 进入主线、活动、幕间或原创章节，并让玩家行为真实改变本局世界线；
- 保存和恢复一份可追溯、不会因模型失败而损坏的游戏状态。

第一份内容验证以迦勒底／冬木相关的最小垂直切片为中心。它用于证明完整游戏循环，不要求一次性实现全量 FGO 内容。

### 1.2 底层工程目标

游戏建立在一套可复用的 **AI World Runtime** 上。底层通过稳定的能力、命令和事件协议，把世界事实与具体实现分离，使角色模型、记忆、TTS、立绘、战斗、地图、剧情和前端可以逐步替换。

两层目标的关系是：

```text
当前交付：可玩的 Fate 风格 Agent Game
                    │
                    ▼
底层约束：可测试、可恢复、可插拔的 AI World Runtime
                    │
                    ▼
长期可能：其他世界包、战斗实现、前端和服务提供者
```

插件化是当前架构要求，但“通用 MOD 市场”“任意语言插件生态”或“支持所有世界类型”不是当前 MVP 的验收条件。

### 1.3 当前明确不做

- 不让 LLM 成为世界数据库或游戏裁判；
- 不要求 NPC 常驻思考或随现实时间无限运行；
- 不在 MVP 中复刻完整 FGO 战斗演出；
- 不一次性人工结构化全部原作剧情；
- 不以移动端、多人联机、VR、全离线模型或正式 MOD 商店作为前置条件；
- 不为了抽象而提前统一所有世界、战斗和角色模型。

## 2. 核心体验方案

### 2.1 主要游戏循环

```text
读取已确认场景
    ↓
观看 NarrativeBeat（叙述 / 对白 / 系统变化）
    ↓
玩家输入自然语言
    ↓
确定性解析或 Pi 输入解释器形成 PlayerAction
    ↓
Runtime 校验、结算并原子提交 GameEvent
    ↓
必要角色获得受限 Observation，返回 AgentAction 提案
    ↓
Runtime 再次裁决并提交
    ↓
前端播放新结果，后台任务异步处理记忆和世界推进
```

### 2.2 三类输入

| 输入通道 | 玩家意图 | 当前处理方式 |
| --- | --- | --- |
| `dialogue` | 对角色说话 | Runtime 校验同场目标，角色 Agent 只基于授权 Observation 回应 |
| `action` | 移动、观察、等待、检查、互动或开放尝试 | 已有规则确定性结算；未知自由行动明确拒绝，等待未来 Resolver |
| `combat` | 指挥、委托或快速结算 | 由 Runtime 的确定性战斗原型结算；玩家不能自行创建战斗 |

自由文本不是世界事实。解析结果也只是候选，只有 Runtime 提交的事件才能改变世界。

### 2.3 前端体验

正式方向是 FGO 对话页与 FSN 阅读体验的混合视觉小说界面：背景、立绘、底部文本区和自由输入共用同一主舞台；地图、档案、角色面板、记录和菜单作为覆层存在。

前端消费两种数据：

- `PlayerVisibleState`：当前玩家有权看到的客观状态；
- `NarrativeBeat`：由已提交事件确定性生成的播放计划。

前端不直接读取数据库，也不能自行判断移动成功、战斗结果、角色知识或剧情进度。

## 3. 不可破坏的设计原则

### 3.1 Program-first, AI-proposes, Runtime-commits

程序拥有规则、权限、状态和提交；AI 只负责理解、表达和提出候选。模型超时、断线或被替换时，可以缺少一次角色回复，但不能产生半次提交或损坏存档。

### 3.2 Kernel owns truth; plugins own behavior

核心拥有跨实现仍然有意义的事实：角色是否存在、在哪里、已确认事件、世界时间、章节进度、伤势或战斗结果等。插件可以决定这些事实如何被计算或呈现，但不能绕过命令权威直接宣布事实成立。

### 3.3 客观事实、主观认知与表现分离

```text
L0 世界事实：GameEvent / GameState
L1-L3 角色视角：证据、情节记忆、关系解释、CIF
表现层：NarrativeBeat、立绘、声音、动画
```

角色可以误解事实；立绘或 TTS 可以表现角色的克制、伪装或情绪，但不能反向改写事实。

### 3.4 所有写入可追溯、可重试、可恢复

- 客观变化必须对应 `GameEvent`；
- 世界快照、事件、可见证据、行动收据和事务内任务一起提交；
- 相同 `actionId` 和相同请求指纹只能产生一次结果；
- 后台任务具有去重键、租约、重试和失败记录；
- 旧事件不静默改写，派生物可依据来源重建。

### 3.5 热路径有预算，冷路径不阻塞玩家

普通对话目标为一次角色模型调用。移动、观察和确定性互动可以零模型调用。L1/L2/L3 记忆、章节评估和世界模拟使用持久任务异步执行。

### 3.6 内容证据与本局现实分离

Atlas 等原作资料是角色初始化、知识边界和章节因果的证据；本局 `GameEvent` 才是已经发生的现实。原作不能覆盖玩家已经改变的世界。

## 4. 总体架构

```text
┌──────────────────────── Presentation ────────────────────────┐
│ Web UI / 未来 Unity 或 Godot                                 │
│ PlayerVisibleState + NarrativeBeat + PlayerAction            │
└────────────────────────────┬──────────────────────────────────┘
                             │ HTTP / SSE
┌────────────────────────────▼──────────────────────────────────┐
│ API / Projection                                                │
│ 输入、可见性投影、事件流、章节与 CIF 管理入口                  │
└────────────────────────────┬──────────────────────────────────┘
                             │ CommandGateway
┌────────────────────────────▼──────────────────────────────────┐
│ Game Runtime / Command Authority                               │
│ 规则校验、串行结算、幂等、事件、世界状态、战斗原型             │
└──────────────┬──────────────────────────────┬─────────────────┘
               │ Observation                  │ atomic commit
┌──────────────▼─────────────┐   ┌────────────▼─────────────────┐
│ Agent + CIF Context         │   │ Persistence                  │
│ Pi 只提出 AgentAction       │   │ SQLite / Event / Job / CIF   │
└──────────────┬─────────────┘   └────────────┬─────────────────┘
               │                               │ committed events/jobs
┌──────────────▼───────────────────────────────▼─────────────────┐
│ Feature Plugins                                                 │
│ 记忆、CIF 演化、剧情、场景、互动协调、世界模拟                 │
└────────────────────────────┬──────────────────────────────────┘
                             │ authorized reads / commands
┌────────────────────────────▼──────────────────────────────────┐
│ Lore + Content                                                  │
│ Atlas 原文、从者资料、章节包、地图包、资源 manifest            │
└───────────────────────────────────────────────────────────────┘
```

### 4.1 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `core` | 公共游戏契约、Runtime、规则与端口 | HTTP、模型 SDK、具体数据库 |
| `platform` | 插件协议、依赖图、生命周期和 Cordis 适配 | 世界规则与业务状态 |
| `plugins/system` | 状态、持久化、命令、地图等基础能力 | 角色表达和剧情策略 |
| `plugins/feature` | 记忆、剧情、场景、模拟等可替换行为 | 绕过命令网关写事实 |
| `cif` | 角色证据、认知、身份、记忆草案和发布 | 充当客观世界状态 |
| `story` | 章节包、世界线、召集、评估和按需模拟 | 无条件强制原作发生 |
| `lore` | 原作资料导入、切片、检索和来源 | 裁定本局事实 |
| `narrative` | 已提交事件到播放块的确定性映射 | 新增世界事实 |
| `api` | HTTP/SSE 和玩家可见投影 | 暴露原始数据库或隐藏状态 |
| `agents` | Pi 模型适配与结构化提案 | 世界写权 |
| `app` | 组合根和进程启动 | 承载可复用业务规则 |

依赖总方向应保持：外部适配层依赖领域契约，领域契约不反向依赖 API、前端或模型 SDK。

## 5. 稳定协议

### 5.1 游戏协议

当前最重要的公共对象是：

- `RawPlayerInput`：未经解释的玩家文本；
- `PlayerAction`：待 Runtime 结算的玩家候选行动；
- `Observation`：某角色本轮被允许知道的场景和输入；
- `AgentAction`：角色台词与行动请求提案；
- `GameEvent`：唯一已确认事实信封；
- `GameState`：当前权威世界快照；
- `NarrativeBeat`：只读、可回放的表现计划。

协议版本化优先于具体语言接口。未来跨进程或跨语言插件应以这些语义定义 JSON Schema / RPC 边界，而不是直接依赖 TypeScript class。

### 5.2 权威命令边界

所有功能插件通过 `world.commandGateway` 请求世界变化。系统层的提交端口只允许系统插件使用；普通 feature 插件不能取得 Runtime、数据库或事务提交器的通用写权。

### 5.3 表现协议的下一层

情绪驱动立绘和 TTS 应增加一个短生命周期的 `PerformanceIntent`，来源可以是 CIF 当前状态与本轮表达策略：

```text
角色心理 / 表达过滤
        ↓
PerformanceIntent
  ├─ expression / pose / intensity
  ├─ voiceStyle / pace / pauses
  └─ presentation fallback
        ↓
PortraitProvider + VoiceProvider
```

`PerformanceIntent` 是本句如何表现，不是新的客观世界事实。没有立绘或语音插件时必须退回文本，不影响游戏继续运行。

## 6. 插件架构

### 6.1 目标

插件系统用于替换能力实现，同时保护世界事实、存档和依赖一致性。插件声明：

- `id`、`version`、`configVersion`；
- `requires` 和 `provides` capability；
- 拥有的事件类型与 durable job 类型；
- 配置、权限和未来的数据迁移要求。

### 6.2 当前已经实现

平台层已经支持：

- composition 启动前的重复 ID、重复 capability、缺失依赖、系统能力越权和循环依赖检查；
- 依赖顺序挂载；
- 运行时注册、启用、停用、移除和状态查询；
- 阻止停用仍被启用插件依赖的 provider；
- 单插件 fiber 销毁以及监听器、定时器和服务 effect 清理；
- 启动失败时的已挂载插件回滚。

当前系统插件包括：

- `system.durable-jobs`
- `system.persistence`
- `system.world-state`
- `system.world-map`
- `system.world-navigation`
- `system.command-authority`

当前功能插件包括：

- `feature.scene-lifecycle`
- `feature.interaction-coordinator`
- `feature.story-chapters`
- `feature.story-summon`
- `feature.world-simulation`
- `feature.memory-consolidation`
- `feature.cif-patterns`
- `feature.memory-evolution-policy`
- `feature.cif-publication`

### 6.3 当前尚未实现

当前“插件”仍是主进程中已经加载的 TypeScript/Cordis 定义，不等于外部插件生态。缺少：

- 外部插件目录和 package discovery；
- 独立 manifest 文件与签名／来源记录；
- 用户启用状态和配置的持久化；
- 安装、升级、回滚和卸载事务；
- 插件数据迁移与 orphan data 策略；
- durable job 的 `ownerPlugin`、`ownerVersion`、`payloadVersion`；
- 文件、网络、数据库、进程和 UI 扩展权限；
- 不受信任插件的进程隔离或沙箱；
- C#、Python、Unity、Godot 等跨进程协议适配。

### 6.4 开发约束

在外部插件管理完成前，新功能仍应先以 capability + 内置插件实现。不能把 `import` 可替换误认为安全安装，也不能承诺卸载一个持久化插件后其数据自动兼容其他实现。

## 7. 数据、事件与持久化

### 7.1 数据层次

| 层 | 内容 | 权威性 |
| --- | --- | --- |
| L0 | 世界快照、确认事件、章节事实、战斗和位置 | 客观权威 |
| 角色证据 | 某角色真正观察到的 L0 | 不等于全知事实 |
| L1 | 单场景情节记忆和暂时感受 | 主观、带来源 |
| L2 | 跨场景关系解释、可错信念、重复目标 | 主观、需生成与审核 |
| L3 / CIF | 身份和长期适应层的版本化修订 | 高约束、可追溯 |
| 表现 | NarrativeBeat、立绘、TTS、动画 | 非权威、可丢弃重建 |

### 7.2 原子提交

一次 Runtime 成功行动应在一个事务中写入：

```text
World State
+ GameEvent batch
+ event recipients / character evidence
+ player private note（若有）
+ bond / story projection 等事务内派生
+ durable jobs
+ processed action receipt + fingerprint
```

其中任何一项失败，整次行动回滚。事务成功后才向插件观察者和 SSE 发布状态。

### 7.3 游戏时间

`GameMoment { timelineId, tick, calendar? }` 与现实时间分离。当前只有确定性 `wait` 推进一个 tick；现实时间只用于日志、重试和租约。未来剧情调度、记忆时间和模拟应优先使用游戏时间。

## 8. 角色、CIF 与 Agent

### 8.1 职责划分

```text
CIF：角色为何这样理解、在意和表达
Context Builder：本轮需要唤醒哪些身份、记忆和证据
Pi Agent：在 Observation 内决定说什么、申请什么
Runtime：这些申请是否成立
Performance：这一句如何被看见和听见
```

### 8.2 首次初始化

原作资料先经过时间线、地区、羁绊和来源过滤，生成带 Source ID 的短证据包；Pi 只能生成草案；程序校验引用和字段；发布器写入正式 CIF。发布 CIF 与角色正式进入世界是两个独立权限动作。

### 8.3 记忆演化

- L1：从场景边界和重要事件生成角色私有情节记忆；
- L2：至少跨多个 L1 证据生成可错认知或关系解释，经过独立审核；
- L3：只允许有多条来源支撑的窄幅适应／表达层修订，追加新版本，不覆盖核心身份；
- 生成器和审核器都不取得数据库通用写权；发布器重新读取存储状态后再提交。

当前 L3 Worker、审核器和发布器已有独立实现与测试，但默认应用组合尚未形成完整自动调度闭环，应标记为“机制已实现、产品接线部分完成”。

## 9. 剧情、世界线与按需模拟

### 9.1 章节模型

主线、活动、幕间和原创内容统一使用 `StoryChapterPackage`。章节目录负责可选择内容；进入章节通过命令网关确认；分支投影只消费已确认事件。

### 9.2 原作与分支

- `session_story_contexts` 保存本局原作锚点与检查点；
- `branch_facts` 保存本局确认事实；
- `branch_progress` 保存实际节点状态；
- `worldline_divergences` 保存原作基线与本局的关键差异；
- `chapter.assessment` 可以结合已确认事件和 Atlas 证据提出带引用草案，但不能自行创造章节事实。

### 9.3 剧情召集和世界模拟

章节节点可以投递 `story.summon`：角色同场时请求受控开场，异地时每个 tick 只沿合法路径接近一步。普通世界模拟也只从确认的 `wait` 生成有限候选，不让所有 NPC 常驻调用模型。

| 前端原型 | NarrativeBeat 播放、逐字显示、点击推进、自动播放、LOG、草稿/播放位置/设置的 localStorage 恢复 |
| 立绘实验 | 玛修图集、表情格浏览和 Canvas 合成验证页 |
| 插件底座 | capability 校验、生命周期、动态启停和依赖保护 |

### 10.2 部分实现

| 领域 | 已有基础 | 仍缺少 |

## 11. 当前主要架构债务

### 11.1 文档状态漂移

旧 `current-status.md`、`project-work-plan.md` 等文件存在已过期的“未实现”描述。后续专题文档应减少重复维护完整状态表，统一引用本文件。

### 11.2 组合根仍直接构造大量依赖

`app/main.ts` 已使用插件 composition，但许多仓储、Runtime、worker 依赖仍在插件外部手工创建并注入。要真正替换实现，需要继续把章节上下文、CIF、Agent、API 和战斗等边界收束为 capability。

### 11.3 PluginManager 尚未成为产品控制面

平台可动态启停进程内插件，但默认应用仍采用启动时静态列表，缺少持久配置、外部发现和管理 API。因此当前不能把底层能力宣传为普通用户可安装 MOD。

### 11.4 `GameRuntime` 职责仍偏重

Runtime 同时承载通用权威规则、具体对象交互和战斗原型。短期应保持行为稳定，后续按已有命令边界逐项提取可替换 resolver，不做一次性重写。

### 11.5 产品闭环落后于底层机制

记忆、世界线和插件机制已经较深，但正式 VN 界面、存读档、地图信息层与首份可玩章节仍不完整。下一阶段必须用可玩闭环约束继续抽象的投入。

## 12. 新开发路线

### 阶段 A：统一事实与稳定基础（当前）

目标：让项目只有一个当前总纲，并保证插件和持久化边界可信。

- 以本文件为项目入口；
- 为插件 job 增加 owner/version/payload version；
- 增加应用优雅停机；
- 将插件启用状态设计为可持久配置，但暂不加载陌生代码；
- 保持完整测试和模块边界检查通过。

验收：能够解释每个已启用插件提供什么、谁依赖它、停用会影响什么、持久任务归谁所有。

### 阶段 B：完成可玩单机闭环

目标：从技术演示进入可以连续游玩的最小游戏。

- 正式 VN 主叙事页；
- 地图、档案、角色面板最小玩家投影；
- 存档位、读档、播放记录一致性；
- 通用自由行动 Resolver 的第一批规则；
- 一份可进入、可偏离、可结束的最小章节。

验收：玩家从新游戏开始，完成一段包含对话、移动、互动和战斗的章节，退出后能准确读档继续。

### 阶段 C：表现层插件

目标：验证“同一角色状态驱动多种表现实现”。

- `PerformanceIntent v1`；
- `PortraitProvider` 和资源 manifest；
- `VoiceProvider`、异步 TTS 队列、缓存与文本回退；
- 情绪／表达策略到立绘和声音参数的确定性映射；
- 无表现插件时保持完整可玩。

验收：替换或停用语音／立绘 provider 不改变存档事实，也不阻止文本游戏继续。

### 阶段 D：外部插件宿主

目标：从“内置插件”升级为“可安装插件”。

- 外部 manifest、版本约束和插件目录；
- 安装／启用／停用／升级／回滚／卸载事务；
- 权限声明和用户确认；
- 数据迁移、孤儿数据和 durable job 处理规则；
- 首批受信任 Service Plugin；
- 管理 API 与 UI。

验收：在测试 profile 中安装、启用、停用、升级和卸载一个无状态 provider，不改代码、不破坏其他插件并可回滚。

### 阶段 E：跨进程和社区扩展

目标：在协议稳定后支持 Python/C#/Unity/Godot 等实现。

- 版本化 JSON Schema；
- RPC 生命周期、健康检查、超时、取消和背压；
- 进程隔离、权限代理和资源预算；
- 内容包与代码插件分级；
- SDK、兼容性测试和签名策略。

验收：一个外部进程 provider 可以被替换、崩溃和恢复，而 Runtime 世界状态保持一致。

## 13. 近期工作优先级

接下来不再同时扩张所有方向，按以下顺序推进：

1. 插件持久任务归属、优雅停机与配置持久化；
2. 正式玩家存档／读档边界；
3. 玩家可见地图、档案和角色面板投影；
4. 第一份最小可玩章节内容；
5. PerformanceIntent + 立绘／TTS provider 验证；
6. 外部插件包管理与权限模型。

新增工作的准入问题：

- 它是否服务当前可玩闭环，或修复一个长期稳定边界？
- 它改变的是世界事实、角色认知、表现，还是工具能力？
- 哪个模块唯一拥有它？
- 是否需要 AI；能否确定性完成？
- 失败后世界是否仍一致且可恢复？
- 如果做成插件，卸载后哪些数据必须继续存在？

无法回答这些问题的功能不进入实现阶段。

## 14. 验证与完成标准

任何里程碑至少满足：

- 新契约有类型和确定性测试；
- Runtime 变化覆盖成功、拒绝、重复提交和提交失败中的相关路径；
- 后台任务覆盖重试和重启恢复；
- 插件变化覆盖启用、停用、依赖阻断和 effect 清理；
- 玩家可见投影不泄露隐藏状态；
- `npm.cmd run check:modules` 通过；
- `npm.cmd test` 全部通过；
- 本文件的实现状态同步更新。

项目完成度不以“写了多少架构”衡量，而以这三个结果衡量：

> **玩家能持续游玩；世界不会因 AI 或插件失败而损坏；核心能力可以在明确协议下逐步替换。**
